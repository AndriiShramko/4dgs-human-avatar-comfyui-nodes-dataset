## Executive Summary

**World Tracing** (arXiv 2606.13652, submitted 2026-06-11) by **World Labs + UIUC** is a single-image / video **generative geometry** model: for each input pixel it predicts an *ordered stack* of camera-space 3D points (XYZ maps), where layer 0 is the visible surface and deeper layers are front-to-back intersections with **occluded** surfaces. It is a depth-estimator-plus-occluded-completion model (a "layered point map" predictor), **not** a camera-pose / SLAM / world-tracking-of-the-camera system despite the name. It is a sibling release to Flex4DHuman (§6.8): overlapping World Labs authorship, adjacent arXiv ID (2606.13652 vs 2606.13655), same week.

**Relevance verdict**: World Tracing does **not** solve our moving-camera / per-frame SE(3) camera-pose gap — that gap (the thing Flex4DHuman §8.3.6 and our v6 plan punt to a VGGT/MegaSaM front-end) stays open; World Tracing recovers *intrinsics from predicted geometry* but not an extrinsic camera trajectory across a moving-camera video. Its actual value to us is a **geometry/occlusion prior** for 4DGS init and for the back-side hallucination problem (our Risk #1). **License blocks all commercial use** (CC BY-NC-ND 4.0 on the repo). Therefore: route to the **NC MVP track only** (6.12/6.13); keep it out of Tracks A/B.

## Technical Relevance to Our Gaps

**Does it close the moving-camera / camera-pose gap? No.** [V/I]
The gap defined in §6.8 (§8.3 item 6) and our v6 plan is: arbitrary in-the-wild monocular video has an *unknown moving camera*, and Flex4DHuman / PRoPE conditioning (§8.1.1) need **per-frame relative SE(3) extrinsics**. World Tracing predicts *per-frame geometry in each frame's own camera space* and recovers *intrinsics*, but it does **not** estimate the camera's extrinsic trajectory / world-consistent registration across a moving-camera sequence. So it is not a VGGT/MegaSaM replacement; that front-end gap remains open. (Note the separately-listed paper "TrackingWorld: World-centric Monocular 3D Tracking" — different work — is closer to that gap and worth a future look.)

**Where it could help instead:**
1. **Occluded-geometry / back-side prior (our Risk #1).** Its core deliverable — geometry *beyond the visible surface* — is exactly the hole-filling problem our 1-step refinement (6.2) and Flex4DHuman's view-generation both attack, but at the *geometry* level rather than the *appearance* level. Layered XYZ could seed/regularize occluded Gaussians.
2. **4DGS init / registration.** Pixel-aligned metric point maps (object/dynamic configs) are a strong initializer for per-clip 4DGS fitting (denser, occlusion-aware vs a single depth map).
3. **Geometry-conditioned novel-view video** is a listed application — conceptually adjacent to Flex4DHuman's dense-view generation, but World Tracing outputs geometry, not RGB views.

**Honest comparison to alternatives we already cite:**
- **vs VGGT / MegaSaM / MASt3R-DUSt3R / Instant4D front-end**: those produce *camera poses* (extrinsics) + multi-view-consistent point maps — i.e. they target our actual gap. World Tracing targets a *different* problem (per-pixel occluded geometry completion), so it is complementary, not a substitute. For the moving-camera front-end, VGGT/MegaSaM remain the right tools.
- **vs MoGe / monocular depth**: World Tracing is strictly richer (multi-layer, occlusion-aware, recovers intrinsics) — but NC-ND, whereas typical monocular-depth options have more permissive terms. For commercial work, prefer the permissive depth/pose stack.

## Integration Sketch — Which Track

**Only the NC MVP track (6.12 / 6.13).** [I, license-driven]
- **NC track use**: as an optional preprocessing/geometry-prior node in the non-commercial demo — input image/clip → World Tracing layered XYZ → occlusion-aware initialization for gsplat 4DGS fitting, and/or as a back-side geometry prior feeding the refinement stage. Inference is cheap (~12-13 s/image at 504², ~30 s for 16-frame at 336² on one A100/H100-80GB, 20 steps, single seed; default 4-seed sweep ≈ 4×).
- **Hard firewall (same as 6.12)**: NC weights/outputs never touch Tracks A/B training or any commercial artifact. CC-ND additionally means we may not publicly redistribute a *modified* version even in the NC demo — call the upstream package, don't fork-and-ship.
- **Caveats**: (a) per-frame camera-space output → still need a separate extrinsics estimator for world-consistent multi-frame stitching; (b) no appearance output (geometry only); (c) metric scale only for object/dynamic configs (scene is relative); (d) 80 GB-class GPU for inference — above our RTX 4090 deployment target, so it is an *offline* preprocessing tool, not an on-device node.
