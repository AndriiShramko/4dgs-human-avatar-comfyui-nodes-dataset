## Executive Summary

ArtiFixer is a **post-hoc 3D Gaussian Splat completion/inpainting model**, not a view-generation-before-fitting model. It takes an *already fitted* sparse-view 3DGS reconstruction (with its rendered RGB + opacity maps) and denoises new/extended views by blending the existing render with noise, weighted continuously by the render's own opacity — dense/observed regions stay close to what was already reconstructed, low-opacity/unseen regions behave like pure generation. It is built on Wan2.1-T2V-14B (~16.9B trainable params) [A], trained in a paper-level "two-phase" recipe that the actual GitHub code implements as **three stages** (SFT → diffusion-forcing finetune → DMD distillation into a causal AR model) [A], and ships as three variants (`ArtiFixer`, `ArtiFixer3D`, `ArtiFixer3D+`) with reported gains over prior SOTA (GenFusion) that are real but benchmark-scope-specific, not a uniform number [B]. **The critical finding for this project: the training/inference code is genuinely Apache-2.0, but the only released pretrained checkpoint is gated under NVIDIA's OneWay Noncommercial License ("research and development only")** [A] — code and weights have different licenses, and only the code is commercially usable as released.

## 23.1 Architecture: Few-Step Causal Autoregressive Diffusion on Wan2.1-T2V-14B

Per the HF model card, read verbatim [A]: *"ArtiFixer is a few-step causal auto-regressive model... This model was developed based on Wan-AI/Wan2.1-T2V-14B-Diffusers."* This is corroborated by WebSearch-indexed arXiv-abstract phrasing ("ArtiFixer is a few-step causal auto-regressive model that enhances and extends 3D reconstruction") [B]. The model's stated inputs (per the HF card) include rendered RGB and **opacity maps from the underlying 3D representation** — i.e., it is architected from the start to consume an existing reconstruction's renders, not to generate views from scratch or from a small set of raw reference photos the way a from-scratch multi-view generator would.

## 23.2 Opacity-Mixing Mechanism

This is the core trick, and it is more precise than a simplified "start from render where geometry exists, start from noise where it doesn't" description. Per WebSearch-indexed project-page text, consistent across ≥2 independent snippets (incl. AlphaSignal coverage) [B]: opacity mixing **"encodes the input RGB into latent space and mixes it with Gaussian noise using the rendered opacity maps."**

- It is a **continuous, per-pixel/per-latent blend weighted by the opacity map** — not a hard binary switch between "denoise from the existing render" and "denoise from pure noise."
- High-opacity regions (Gaussians present, well-observed by the sparse input views) → the denoising process starts close to the existing render and stays faithful to it.
- Low-opacity regions (holes, unseen/occluded areas) → the process behaves close to pure generation, i.e., the model effectively hallucinates content there, conditioned on everything else in the scene.
- The HF model card's listed inputs ("Rendered RGB and opacity maps from the underlying 3D representation") are consistent with, and corroborate, this mechanism [A], though the exact mathematical formulation of the blend was not read from a primary source (arXiv PDF was 403'd) — treat the *behavioral* description above as confirmed, the *precise math* as ⚠️ unverified.

This mechanism is architecturally elegant for the "faithful where observed, plausible where not" framing — but note it is defined and demonstrated on a **static** (or at most quasi-static) 3D Gaussian scene's opacity field, not on a time-varying opacity/occupancy field for an articulated, moving human (see §23.9).

## 23.3 Training Recipe: Paper's "Two-Phase" Framing vs the Repo's Three Code Stages

WebSearch-indexed snippets describing the paper consistently frame training as **two phases** [B]: *"In Phase I, it finetunes a bidirectional video diffusion model using an opacity mixing strategy... In Phase II, it distills the bidirectional teacher into a causal autoregressive model via Self-Forcing-style DMD distillation. The resulting model generates hundreds of frames in a single pass."*

The GitHub repo's own `README.md`, fetched **verbatim via curl** [A], describes this as **three code-level stages**, which is the more precise and load-bearing description:

| Stage (code, [A]) | What it does | Maps to paper "Phase" ([B]) |
|---|---|---|
| **Stage 1** | Supervised finetuning on reconstruction-conditioned DL3DV clips | Part of Phase I |
| **Stage 2** | Diffusion-forcing finetune (block-causal masking) from Stage 1 | Part of Phase I (bidirectional teacher + opacity mixing) |
| **Stage 3** | DMD distillation, using Stage 2 as student/generator and Stage 1 as critic | Phase II (distillation into causal AR) |

This is not a contradiction — Phase I (paper-level) corresponds to Stages 1+2 (building the bidirectional/diffusion-forcing teacher), Phase II corresponds to Stage 3 (distillation) — but "two-phase" is a paper-level simplification of a three-stage training recipe. The Stage-3 output is the causal AR model that "generates hundreds of frames in a single pass" [B] — this long-rollout, single-pass generation is directly relevant to temporal-consistency questions (§23.9).

## 23.4 Three Variants: ArtiFixer / ArtiFixer3D / ArtiFixer3D+

The HF model card's evaluation table lists exactly three rows — `ArtiFixer`, `ArtiFixer 3D`, `ArtiFixer 3D+` — each with its own PSNR/SSIM/LPIPS/FID on Nerfbusters (NB) and DL3DV [A]. The GitHub README (verbatim via curl) [A] describes the mechanics of each:

| Variant | Mechanism | Output |
|---|---|---|
| **ArtiFixer** | Direct frame generation from the diffusion model, conditioned on renders/opacity from a sparse reconstruction | New/completed **views** (2D video frames), not yet re-fused into 3D |
| **ArtiFixer3D** | Trains a **fresh 3DGRUT optimization** on the union of real anchor views + ArtiFixer-generated target views | Distills the generated views back into an actual **3D Gaussian representation** |
| **ArtiFixer3D+** | A second ArtiFixer pass applied to renders **from the improved ArtiFixer3D reconstruction** | ArtiFixer run again, as a **post-processing** step on top of ArtiFixer3D's own output |

This is a self-reinforcing pipeline: generate views → re-fit 3D from them → generate again from the better 3D → (optionally) re-fit again. Note that individual per-variant benchmark numbers beyond the one ArtiFixer3D figure below were **not extracted** from a primary source this session — the HF table exists and has three rows, but only one number was read out; see §23.5.

## 23.5 Benchmarks vs GenFusion

- **Directly read from a primary source [A]**: on the HF model card's Nerfbusters/DL3DV table (Difix3D+ evaluation protocol), **ArtiFixer3D scores 20.24 PSNR (Nerfbusters) / 20.14 PSNR (DL3DV)**. This is the only numeric benchmark figure confirmed from a primary-source read this session — GenFusion's number on that same table, and the ArtiFixer / ArtiFixer3D+ rows' numbers, were **not extracted**.
- **WebSearch-indexed, consistent across sources [B]**: *"ArtiFixer variants outperform GenFusion by almost 3 dB in PSNR... presented in Table 3 of the ArtiFixer paper, which focuses on novel content generation evaluation."* A broader claim across all benchmarks states "1–3 dB PSNR" over prior SOTA generally.
- **Net assessment**: the "~3 dB over GenFusion" headline is accurate but **scope-specific** — it is Table 3's novel-content-generation setting, not a uniform gap on every benchmark/variant. Because the exact GenFusion PSNR value used to compute that delta was only found via secondary summary (not a table read directly), the precise number **cannot be independently cross-checked** from what was verified this session. Treat "≈3 dB over GenFusion" as **plausible and likely directionally correct**, not as a number to quote as independently confirmed.

## 23.9 Relevance to Our Project

**The core structural difference: ArtiFixer completes a splat *after* fitting; our plan generates views *before* fitting.**

| Dimension | ArtiFixer (NVIDIA) | Our planned Stage A (§6.13 / §6.16 / §6.19 / §6.21) |
|---|---|---|
| Point of intervention | **Post-hoc** — operates on an *already-fitted* 3D Gaussian representation, consuming its renders + opacity maps | **Pre-hoc** — a separately fine-tuned generative video model produces extra reference *views* (frames), which are then fed **into** 4DGS fitting alongside the real frontal captures |
| Conditioning signal | Continuous opacity-weighted blend of render latent + noise, per pixel | PRoPE 5-axis positional encoding; SE(3)-aware cross-view/cross-time attention conditioned on the real frontal reference pair (§8.1.1) |
| Base model | Wan2.1-T2V-**14B** (~16.9B trainable) | Wan2.1-**1.3B** |
| Training data (as released) | DL3DV — general real-world, largely static/quasi-static scenes | PKU-DyMVHumans + CMU Panoptic + AIST++ + self-rendered synthetic — **human-specific**, multi-view, dynamic (§6.17/§6.19) |
| Confirmed temporal/4D human handling | None found; causal-AR distillation targets long-rollout *video* consistency, but demonstrated on static/quasi-static 3D scenes, not documented articulated humans | Explicit dynamic-human curriculum: PRoPE + temporal rollout, T≤16 stages, temporal regularizers at the 4DGS-fit stage (§6.3, §21.7 audit item 3) |
| Released-weights license | NVIDIA OneWay Noncommercial — research/dev only | N/A — trained in-house on data already cleared for the NC track (§6.12); commercial Track A firewalled per §6.7/§6.12 |
| Compute to reach a usable state | Zero *if* the released NC weights transfer to our domain (unverified) — but a from-scratch retrain of a 14B model is a much larger commitment than the already-budgeted 1.3B fine-tune | Budgeted: **~5–8 calendar weeks / 7–14 GPU-days** on 1×96 GB card (§6.13 S2, red-team-audited) |

### Could ArtiFixer be a cheaper/faster Layer-0 alternative or complement to Stage A?

**The idea is architecturally plausible and worth testing, but nothing in what was verified this session supports assuming it would work out of the box, and it should not be treated as a substitute for Stage A without evidence.** Concretely:

1. **The mechanism maps unusually well onto our own "faithful front / hallucinated back" framing.** Opacity mixing — denoise-from-render where opacity is high, denoise-from-noise where opacity is near zero — is almost exactly the shape of the problem this project already committed to (§6.16 owner correction, §6.21 §21.0: "any view you do NOT provide is generated by the model"). A Layer-0 4DGS fit of a 2-GoPro frontal capture (§6.16 Path A, zero-training) would produce a splat with opacity ≈1 in front and opacity ≈0 on the back — precisely the input shape ArtiFixer is designed to consume. In principle, one could run Layer 0 to get the sparse frontal splat, then run ArtiFixer's opacity-mixing pass on renders from novel back-facing camera poses to fill in the unseen Gaussians directly — **without training a dedicated hallucination model at all**, i.e. as a candidate replacement for, or supplement to, the entire Stage-A fine-tune in §6.13/§6.21.
2. **But the domain mismatch is a first-order problem, not a detail.** Everything verified about ArtiFixer's training data (DL3DV) and demonstrated use points to **general, largely static/quasi-static real-world scenes** — rooms, objects, outdoor captures. Nothing in the verified sources shows it trained or evaluated on **articulated, clothed, moving humans**, and nothing shows it handling **per-frame-varying (4D) content** rather than a single static reconstruction. Our problem is specifically a deforming-human, temporally-coherent-video completion problem. Transfer from "fill in the unseen side of a static room" to "plausibly and stably hallucinate the back of a moving, gesturing person across dozens of frames" is a real generalization gap, not a minor caveat — this is the same class of gap §6.16/§6.19 already flagged for general-scene tools like DimensionX ("general scenes, not human-faithful; identity hallucinated").
3. **What would have to be true for ArtiFixer to genuinely substitute for (not just complement) Stage A:**
   - It would need **retraining or fine-tuning on human-specific, articulated, multi-view, dynamic data** — almost certainly the same PKU-DyMVHumans / CMU Panoptic / AIST++ / GoPro-turntable data this project already plans to use for Stage A (§6.17, §6.21 §21.2). That does not eliminate the data-acquisition or training-time cost §6.13 already budgets; at best it swaps *which* base architecture absorbs that cost (ArtifixerTransformer/Wan2.1-14B vs. our planned Wan2.1-1.3B+PRoPE), and a 14B base is a **much larger** single-GPU commitment: scaling §13.3's own VRAM accounting (statics ≈21 GB for the 1.3B model at full FT) by roughly the parameter-count ratio implies full-FT statics well beyond what fits comfortably on one 96 GB card without LoRA-only training or aggressive offload — this could break the single-box, weeks-not-months feasibility case that makes §6.13's plan tractable at all. Evaluating this properly (rather than assuming it's "free" because the checkpoint exists) is exactly the kind of comparison §6.19's Layer-2 "watch and upgrade" track already does for Forge4D — ArtiFixer belongs in that same bucket, not in Layer 0.
   - Its causal-AR long-rollout generation ("hundreds of frames in a single pass," §23.3) is a genuinely relevant precedent for the **#1 documented quality risk in this project's own back-hallucination plan**: flicker from temporally inconsistent generated views (§6.21 §21.6 audit finding 3, §6.3 temporal regularizers). If ArtiFixer's DMD-distilled causal AR model is temporally consistent by construction the way Self-Forcing-style distillation is designed to be, that is independent evidence that this architectural pattern (bidirectional teacher → causal-AR distillation) is a viable route to flicker-resistant long rollouts — supporting a design choice this project is already leaning toward, even if the specific checkpoint isn't reusable.
   - **License compatibility with Track A vs Track C (§6.7, §6.10, §6.12)**: the code (Apache-2.0) is compatible with commercial Track A in principle, matching the "Low risk" component pattern §6.7's license map already applies to gsplat/MHR/Anny. But the only released checkpoint is gated NC ("research and development only") — under the same firewall logic §6.12 §12.3 already applies to MV-Performer, Diffuman4D, and Sapiens, **that checkpoint could be evaluated on the NC track (Track C) but must never enter Track A infrastructure, and no synthetic data or pseudo-labels it produces may inform commercial-track training** — not even as an intermediate research signal, per the existing firewall rules (§12.3 item 3). Using ArtiFixer's *approach* commercially would require retraining the architecture from scratch on our own licensed data under the Apache-2.0 code, which is a large compute investment additional to (not a discount on) the work already budgeted in §6.13.
4. **A cheap, concrete, unrun experiment that would actually answer this**, sized for the Track C / NC-MVP process already in place (§6.12): download the released NC checkpoint, run a Layer-0 2-GoPro 4DGS reconstruction (§6.16 Path A, zero training already required), and apply ArtiFixer's opacity-mixing pass zero-shot to novel back-facing renders of a real subject — purely as an NC-track qualitative probe, never feeding its output into Track A training (§12.3 firewall). This is a half-day-to-a-day experiment, dramatically cheaper than committing 5–8 calendar weeks (7–14 GPU-days) to Stage A on the assumption that a dedicated human-specific fine-tune is required. **This experiment has not been run.** A clearly positive zero-shot result (plausible, stable-looking human backs) would be strong evidence to promote ArtiFixer from a Layer-2 watch-item to an active Stage-A alternative or pre-training initializer; a clearly negative result (the domain gap in point 2 above dominates) would confirm the current plan's approach is still the right one and this becomes a documented-and-closed evaluation rather than an open question.

**Bottom line**: ArtiFixer is not evidence that Stage A can be skipped — its released weights are general-scene, non-commercial, and unproven on humans or on 4D content. But its architecture is independent, recent (per task framing: SIGGRAPH-2026-class) validation of two design choices this project has already converged on (opacity/observation-conditioned generation for the seen/unseen split; causal-AR distillation for long, hopefully-consistent rollouts) — and it is cheap enough to test directly against our own Layer-0 output before spending further GPU-weeks. **Flagged as an open question for the team to test, not a conclusion.**
