## Executive Summary

The v5 plan correctly identifies MEGA (ICCV 2025) as a strong compression framework, but **fails to acknowledge its limitations** (high-frequency detail loss from SH decomposition, potential "flickering holes" from opacity entropy penalty) and **ignores newer alternatives** that achieve comparable or superior compression through fundamentally different approaches. P-4DGS (2025) adapts video-codec-inspired prediction (anchor-based intra/inter prediction) for up to 90x compression, OMG4 uses Sub-Vector Quantization, and Temporal Smoothness-Aware RD-Optimized 4DGS (NeurIPS 2025, referred to as "RD4DGS" below) achieves up to 91x via wavelet transforms. The recommended strategy: **MEGA DC-AC decomposition as the base** (proven, well-understood) + **anchor-based spatial-temporal prediction from P-4DGS** for animation sequences + **entropy coding** from RD4DGS for bitstream optimization.

## SOTA Analysis 2025-2026

### 6.1 MEGA Architecture (ICCV 2025) — Deep Analysis

**DC-AC Decomposition**:
- Per-Gaussian: Only DC color (3 RGB values) stored as attributes
- Shared lightweight MLP (3 linear layers, the "AC color predictor") computes view/time-dependent color from Gaussian position, view direction, and time: c(x,d,t) ≈ σ(MLP_φ(sg(x), sg(d), t, c_DC)) ⚠️ [fact-check 2026-06-12: formula is a paraphrase; the paper confirms the MLP inputs and the use of a stop-gradient operation on inputs, but the exact equation form here is reconstructed, not quoted]
- Stop-gradient (sg) prevents color gradients from corrupting geometry attributes (confirmed in paper)

**Opacity Entropy Regularization**:
- Loss term: L_entropy = -Σ [α_i · log(α_i) + (1-α_i) · log(1-α_i)]
- Forces Gaussians to commit: fully visible (α→1) or fully invisible (α→0)
- Invisible Gaussians are pruned → drastic count reduction

**Compression pipeline**:
1. SH removal: 161 → 20 parameters per point (144 SH coefficients replaced by 3 DC color values; ~8x attribute compression per the paper) ⚠️ [fact-check 2026-06-12: corrected from "161 → 17 (9.5x)"]
2. Gaussian count reduction: e.g., 13M → 0.91M on the Technicolor *Birthday* scene (~14x count compression)
3. Half-precision (FP16) storage + zip compression: further memory reduction
4. Total: ~190x compression on Technicolor, ~125x on Neural 3D Video

### 6.2 Known MEGA Limitations

**Problem 1: Specular Detail Loss**

The shared MLP approximates a global appearance function. Per-point specular highlights (e.g., the precise catchlight in an eye, metallic jewelry reflections) that depend on the specific micro-geometry of individual Gaussians are averaged out. The MLP learns the dominant color patterns but not point-specific anomalies.

⚠️ [fact-check 2026-06-12: the previously stated evidence "~0.5-1.0 dB PSNR degradation on specular scenes" could not be found in the MEGA paper or its ablations; the paper claims comparable rendering quality to 4DGS. The specular-loss mechanism described above is a plausible theoretical concern, but its magnitude is unquantified — verify with our own avatar close-up test before treating it as a blocker.]

**Problem 2: Flickering Holes Risk**

The opacity entropy penalty drives α toward binary values. During animation, as Gaussians deform:
- A Gaussian near the α=0.5 threshold may flip between visible and invisible across frames
- This creates "flickering holes" — momentary gaps in the surface
- More pronounced in regions with rapid motion (cloth edges, hair tips)

The binary enforcement assumes Gaussians are either definitively part of the surface or not. In reality, semi-transparent Gaussians serve important roles at surface boundaries.

**Problem 3: MLP Inference Cost**

The shared MLP must be evaluated for every visible Gaussian at every frame. For <1M Gaussians with a 3-layer MLP:
- ~1M MLP forward passes per frame (one per visible Gaussian) ⚠️ [fact-check 2026-06-12: corrected from "~3M evaluations"; 3 layers ≠ 3 evaluations]
- Each forward pass: on the order of 10^3-10^4 FLOPs for a small 3-layer MLP (depends on hidden width) ⚠️ [fact-check 2026-06-12: corrected from "~100 FLOPs", which understated even a tiny MLP]
- Total: roughly 1-10 GFLOPs per frame — still small relative to RTX 4090 throughput (~80 TFLOPS FP32); MEGA reports rendering speeds comparable to 4DGS
- But: Memory access pattern is irregular (scattered Gaussian positions as MLP input), causing cache misses

### 6.3 P-4DGS: Video Codec Techniques for 4DGS (2025)

P-4DGS ("P-4DGS: Predictive 4D Gaussian Splatting with 90× Compression", arXiv:2510.10030) adapts the *principles* of intra-/inter-frame prediction from video compression to dynamic Gaussian scenes:

**Key innovation**: Instead of storing each Gaussian's attributes independently, P-4DGS exploits spatial-temporal redundancy. ⚠️ [fact-check 2026-06-12: the earlier description of explicit "keyframes (I-frames) at regular intervals + per-frame deltas (P-frames)" does not match the paper. P-4DGS stores NO explicit keyframes or residual deltas — prediction errors are absorbed into learned anchor/MLP parameters. Corrected mechanism below.]

1. **Intra-frame (spatial) prediction**: 3D anchor points in canonical space; nearby Gaussians' attributes are predicted from anchor features via lightweight MLPs (Scaffold-GS-style), reducing the number of stored primitives
2. **Inter-frame (temporal) prediction**: a deformation MLP predicts per-Gaussian deformation (Δx, Δs, Δr) from canonical space to any timestamp using positional/time encodings
3. **Adaptive Quantization**: quantization strategy applied to anchor attributes
4. **Context-based Entropy Coding**: learned context models for entropy coding of anchor data

**Results** (verified against paper/abstract):
- ~40x compression on D-NeRF and ~90x on NeRF-DS (dataset-dependent, monocular deformable-scene benchmarks — *not* multi-view human avatar data)
- <1 MB storage per scene
- Real-time rendering reported (>260 FPS)
- Comparable or improved rendering quality vs baselines

**Relation to MEGA**: ⚠️ [fact-check 2026-06-12: the earlier claim "P-4DGS preserves per-point SH coefficients (compressed, not removed)" appears incorrect — likely hallucinated. P-4DGS predicts Gaussian attributes (including appearance) from anchor features via MLPs; like MEGA, it does not keep full per-point SH. The claimed specular-detail advantage over MEGA is therefore unsupported.]

### 6.4 OMG4: Sub-Vector Quantization for 4D (2025)

Optimized Minimal 4D Gaussian Splatting uses a three-stage progressive pipeline:

1. **Gaussian Sampling**: Identify critical primitives using importance scoring
2. **Gaussian Pruning**: Remove redundant primitives via contribution analysis
3. **Gaussian Merging**: Fuse similar nearby primitives into single larger Gaussians

Plus **Sub-Vector Quantization (SVQ)**: Partition each Gaussian's parameter vector into sub-vectors and quantize each sub-vector independently using a learned codebook.

**Results**: >60% model size reduction with minimal quality loss.

### 6.5 "RD4DGS": Temporal Smoothness-Aware Rate-Distortion Optimized 4DGS (NeurIPS 2025)

⚠️ [fact-check 2026-06-12: "RD4DGS" is not the paper's name. The real paper is "Temporal Smoothness-Aware Rate-Distortion Optimized 4D Gaussian Splatting", arXiv:2507.17336, NeurIPS 2025 (also on OpenReview). Content claims below verified against it.]

Applies end-to-end rate-distortion optimization on top of a static/dynamic-decomposed 4DGS (Ex4DGS):

1. **Wavelet Transform**: Pointwise wavelet transform reflecting temporal smoothness priors in motion trajectories
2. **RD-Guided Quantization**: Adaptive rate-distortion guided quantization (flexible rate-quality trade-off)
3. **End-to-End RD Optimization**: Compression framework optimized jointly with reconstruction quality

**Results**: Up to 91x compression vs the original Ex4DGS model (down to ~1.1% of original size) while maintaining visual fidelity. The expectation that the wavelet approach favors smooth motion (walking, gesturing) over stochastic motion (cloth flutter) is our inference from the temporal-smoothness prior, not a reported ablation.

## Critical Analysis

### Risk 1: ComfyUI Integration Complexity

ComfyUI operates as a node-based workflow system. Integrating a custom 4DGS renderer requires:

1. **Custom node development**: Python node wrapping gsplat rasterizer
2. **Memory management**: ComfyUI's model management system must handle 4DGS scene loading/unloading
3. **Real-time preview**: Interactive viewport requires 30+ FPS rendering during node graph editing
4. **Compatibility**: Must work alongside existing ComfyUI nodes (image processing, ControlNet, etc.)

**Estimated development effort**: 4-6 weeks for a production-quality ComfyUI node.

### Risk 2: Dynamic Scene Streaming

For 10-second avatar animations at 60 FPS, a naive per-frame attribute dump would be:
- 600 frames × ~1M Gaussians × 20 params × 2 bytes (FP16) ≈ 24 GB ⚠️ [fact-check 2026-06-12: corrected from "17 params ≈ 20 GB"; also note this is a hypothetical worst case — MEGA and P-4DGS are 4D representations whose Gaussians/anchors are shared across time, so neither actually stores per-frame snapshots]
- A MEGA-compressed dynamic scene is on the order of tens of MB (e.g., ~190x vs original 4DGS model size on Technicolor) ⚠️ [fact-check 2026-06-12: the earlier "~105 MB" came from dividing the naive per-frame dump by 190x, which misapplies the ratio — 190x is measured against the original 4DGS *model*, not a frame dump]
- With P-4DGS-style anchor + deformation-MLP encoding: ~1 MB per scene on its benchmarks (D-NeRF/NeRF-DS); for a higher-fidelity 1M-Gaussian avatar clip, ~10-20 MB is our extrapolated engineering target, not a published result

P-4DGS-style spatial-temporal prediction is critical for streaming scenarios.

### Risk 3: Decompression Latency

MEGA requires MLP inference at render time (online decompression). P-4DGS requires anchor-MLP attribute prediction + deformation-MLP evaluation. Both add latency:

| Method | Decompression overhead per frame | Impact on 60 FPS budget |
|--------|--------------------------------|------------------------|
| MEGA MLP | ~0.5 ms | Acceptable (3% of frame budget) |
| P-4DGS anchor + deformation MLP | ~1-2 ms | Acceptable (6-12% of frame budget) |
| OMG4 codebook lookup | ~0.1 ms | Negligible |

⚠️ [fact-check 2026-06-12: the millisecond figures above are our engineering estimates, not numbers from the papers. Indirect support: MEGA reports rendering speeds comparable to 4DGS, and P-4DGS reports >260 FPS (<4 ms/frame total) on modern GPUs — so the order of magnitude is consistent.]

All methods are compatible with real-time rendering on RTX 4090.

## Architectural Recommendations for MVP

### Hybrid Compression Pipeline

```
Training Output (13M Gaussians × 161 params)
                ↓
        MEGA DC-AC Decomposition
        (remove SH → DC only + shared MLP)
                ↓
        Opacity Entropy Pruning
        (13M → <1M Gaussians)
                ↓
        P-4DGS-style Spatial-Temporal Prediction
        (anchors + deformation MLP; our format may add
         explicit keyframes/deltas for random access —
         a design extension, not part of P-4DGS itself)
                ↓
        Entropy Coding (arithmetic)
                ↓
        Compressed 4DGS File (target: ~10-20 MB per 10s clip — extrapolated, unvalidated)
                ↓
        ComfyUI Custom Node (gsplat renderer)
```

### Key Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| SH handling | MEGA DC-AC (remove SH, use shared MLP) | Proven ~8x per-point attribute compression (161 → 20 params); specular loss acceptable for MVP (magnitude unquantified — needs our own test) |
| Density reduction | Opacity entropy + importance pruning | Reduces from 13M to <1M (MEGA: 13M → 0.91M on Technicolor Birthday); critical for 24 GB VRAM target |
| Temporal compression | P-4DGS-style anchor + deformation-MLP prediction (optionally with our own keyframe/delta layer for random access) | Exploits temporal redundancy; P-4DGS reports up to 90x total on its benchmarks; additional gain for our avatar clips is an estimate |
| File format | Custom binary with header + keyframes + deltas | Efficient streaming; random access to any frame via nearest keyframe |
| Renderer backend | gsplat (Apache 2.0) | Legally safe; superior VRAM efficiency; packed sparse tensor support |
| Target VRAM budget | <16 GB for scene data (leaving 8 GB for pipeline) | Fits RTX 4090 with headroom for ComfyUI overhead |

## Open Questions

1. **MEGA vs preserving SH**: For avatar close-ups (face), is MLP-approximated color sufficient, or do we need per-point SH for eye specular highlights? Requires visual quality test.
2. **Keyframe interval (our format)**: If we add a keyframe/delta layer on top of anchor-based prediction for random access, what interval (every 10, 30, or 60 frames) provides the optimal compression/quality trade-off for human avatar motion? (Note: P-4DGS itself has no keyframes — this is our own format question.)
3. **ComfyUI model caching**: How to handle multiple avatar scenes in ComfyUI without exceeding VRAM? Need LRU eviction strategy.
4. **Progressive loading**: Can we stream the first keyframe for instant preview and load deltas progressively? Important for user experience.
5. **WebGPU export**: For web-based deployment (beyond ComfyUI), can the compressed format be directly rendered in browser via WebGPU/WebGL?
