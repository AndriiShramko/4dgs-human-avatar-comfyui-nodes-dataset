## Executive Summary

1. **Six agents, one GPU, one goal loop.** A lean roster (Team-Lead, Infra, Data, Training, Eval, Integration) runs unattended between milestone gates. The single RTX 6000 Pro forces strict queue discipline: exactly one training process owns the GPU; eval and preprocessing run in training gaps or on CPU.
2. **Milestones M0→M6** map directly to the §8.1.1 curriculum: env+smoke → data ready → stage-1 (1r1t) → stage-2 (dynamic N_ref) → stage-3 rollout → 4DGS end-to-end demo → public NC release. Each gate has measurable entry/exit criteria; the Team-Lead may not advance a milestone without the Eval agent's signed metrics file.
3. **Owner decides; agents execute.** Owner-only decisions: dataset license acceptances (DNA-Rendering gate), any public publishing, scope cuts that change the MVP definition, and spending. Everything else — hyperparameters within bounds, failure recovery, scheduling — is autonomous, logged, and reversible.
4. **Clean-room is relaxed for this NC track (recommended stance, documented in §14.4):** agents MAY read reference code (PRoPE reference impl, Diffuman4D, MV-Performer) to resolve spec ambiguities, but our training code stays Apache-2.0, no verbatim copying from non-permissive sources, and a provenance log records what was consulted per module. Consequence (per §12.3 rule 5): this codebase and its authors' "read set" are firewalled from Track A's clean-room implementation side — Track A receives only facts/measurements from this track.
5. **Everything restartable from manifest + last checkpoint.** The hard operational invariant: at any moment, killing every process and rebooting the box must lose at most one eval interval of work.

## 14.2 Goal-Mode Mechanics

**Milestone gating.** A milestone is a directory `state/milestones/M{n}/` containing: `criteria.yaml` (machine-checkable where possible), `evidence/` (Eval-signed metrics, artifact hashes), `decision.md` (Team-Lead go/no-go + rationale). Gate rule: Team-Lead advances only when every exit criterion has linked evidence; any owner-gated criterion requires a recorded owner reply (vault note or chat) referenced by path/date.

**Single-GPU queue discipline.**
- One training process owns the GPU at a time, enforced by a lock file + `nvidia-smi` check before any CUDA job; violators self-terminate.
- Priority: active curriculum stage > eval of latest ckpt > latent precompute > ablations/distillation experiments.
- Eval/preprocessing scheduling: evals run at checkpoint boundaries (training auto-pauses ≤ one eval batch) or on CPU where possible (LPIPS on GPU in the pause window; SSIM/PSNR on CPU). VAE latent precompute for the *next* stage runs in scheduled nightly gaps, never concurrent with training.
> ⚠️ [red-team 2026-06-16: cadence tension with §6.13. §6.13 §13.7 wants a fixed eval pack every **2k iters**; a full diffusion eval (40 denoise steps × CFG = 80 fwd passes per clip × multi-view) on the *same single GPU* is not "≤ one eval batch" — at L=16k it can be 20–60 min of GPU time per eval, i.e. several % of throughput if run every 2k iters. Two fixes: (1) use a **cheap fast-val** (fewer steps / fewer clips / 256² proxy) at the 2k cadence and reserve the full 40-step eval for ckpt-keep boundaries only; (2) make explicit that eval GPU time is **counted inside the §6.13 wall-clock**, not free — the §6.13 calendar correction (×2) already partly covers this, but state it so the two docs agree. Also: VAE precompute "in nightly gaps" assumes training has gaps; a 24/7 stage has none — precompute then steals a contiguous 1–3 day slot from the queue (additive to calendar).]
- 96 GB VRAM is the budget ceiling: micro-batch and view-count per stage chosen by an automated binary search at stage start (per §6.13 envelope), then frozen for the run.

**Checkpoint/eval cadence.** Checkpoint every N optimizer steps (N per stage, set at stage start; cadence cost per §6.13); keep last 3 + best-by-val + one per 10k steps; Infra GC enforces a disk quota [target: ckpt pool ≤ 1.5 TB]. Every kept ckpt gets a fast-val (10 clips) score; full val per milestone.

**Automatic failure playbooks (no owner involvement):**
| Trigger | Detection | Action |
|---|---|---|
| OOM | CUDA OOM exception | Halve micro-batch → if still OOM reduce views/frames per §8.1.1 layout options → enable block-swap (musubi-tuner, §6.9 ref 4) → resume from last ckpt |
| Divergence | loss > 3× trailing median for 200 steps, or NaN | Rollback to last good ckpt, LR ×0.5, re-run; 2 consecutive failures → freeze run, escalate |
| Data corruption | decode/shape/NaN error in loader | Quarantine shard (move to `data/quarantine/`, log manifest entry), continue; >2% shards quarantined → pause stage, Data agent audit |
| Silent quality drop | fast-val PSNR drops >0.5 dB [target] across 2 consecutive ckpts | Flag in daily status; 3 consecutive → auto-rollback to best ckpt + escalate |
| Box reboot / session death | Team-Lead heartbeat stale >30 min | systemd/startup script relaunches Team-Lead; it replays `state/queue.jsonl`, resumes training from last ckpt (bitwise-resumable optimizer state required from M0) |

**Owner-decision boundary.** OWNER: license/gate acceptances (DNA-Rendering, any gated ckpt), anything leaving the machine (repo push, HF upload, demo page, author emails), milestone-definition changes, purchases. AGENTS: LR/schedule within ±4× of spec defaults, batch/view layouts, recovery actions above, eval additions, refactors. Ambiguity defaults to "ask" with a 24 h timeout → safe default = do nothing externally visible.
> ⚠️ [red-team 2026-06-16: **owner-absence stall**. The "24 h timeout → do nothing externally visible" default is safe for *external* actions but is a **silent productivity killer at owner-only gates** (M1, M6) and at any escalation: if the owner is travelling for a week, the box sits idle waiting on a license click or a go/no-go. Mitigations to add: (1) **non-blocking gate ordering** — agents continue all *non-gated* downstream work (e.g., build the synthetic render pipeline, write eval harness, scaffold ComfyUI nodes) while an owner gate is pending, so GPU/calendar is never idle on owner absence; (2) an **owner-absence SLA**: pre-authorize the safe fallback per gate (e.g., "if no reply in 72 h at M1, proceed on the synthetic-first branch") so the program self-progresses on the conservative path rather than freezing; (3) the daily-line reporter should explicitly surface "BLOCKED ON OWNER since <date>" so the stall is visible, not buried.]

## 14.4 Engineering Scaffold

- **Repo layout** (single private repo until M6): `train/` (model, PRoPE, curriculum — Apache-2.0), `data/` (manifests + scripts; no payloads in git), `eval/` (harness, frozen-set hashes), `fit4dgs/` (gsplat pipeline), `comfy_nodes/`, `state/` (gitignored), `docs/provenance/`.
- **Clean-room decision (recommended): clean-room is OPTIONAL for this NC track and we relax it.** Rationale: the deliverable is NC-labeled regardless (data provenance), so the commercial value of "never read their code" accrues to Track A, not here. Pragmatic stance: (1) may read PRoPE reference code and Diffuman4D/MV-Performer code to resolve ambiguities; (2) no verbatim copying from non-Apache/MIT sources — re-implement from understanding; (3) `docs/provenance/read_log.md` records every external source consulted per module; (4) hard rule unchanged from §12.3: nothing from this repo (code, weights, synthetic outputs) enters Track A, and Track A's implementation side treats this repo as unreadable. This preserves the option to run Track A as a true clean-room later.
- **Experiment tracking, wandb-free:** tensorboard event files + append-only `train_log.jsonl` / `eval/.../metrics.json`; one `runs/<run_id>/config.yaml` fully determines each run (seed, data manifest hash, env.lock hash). A run is invalid if its config hash is unrecorded.
- **Dataset manifests with provenance:** every shard row = `{shard_id, source, license, owner_acceptance_ref, preprocessing_version, sha256}`. NC labeling is per-shard, enabling later subsetting if a clean-data retrain (Track A) reuses the pipeline.
- **Eval sets frozen at M1**, hashes recorded in `eval/FROZEN.md`; any change to frozen sets is an owner-gated event and resets comparability (old metrics archived, not deleted).

## 14.6 Risks Specific to Agent-Driven Training

| Risk | Mechanism | Mitigation |
|---|---|---|
| Silent metric drift | harness or data change shifts numbers without code "failing" | Eval harness versioned; metrics signed with ckpt+frozen-set+harness hashes; golden-ckpt regression test (re-score a fixed M2 ckpt weekly — must reproduce within 0.05 dB) |
| Agents over-tuning on val | autonomous LR/config tweaks optimize the 10-clip fast-val | Decision rule: config changes may use fast-val; **gate decisions use the full frozen val touched only at ckpt boundaries; test set (16 scenes) touched once per milestone by Eval only**; Training agent never reads test metrics |
| Disk filling with checkpoints | unattended runs × ~14 GB ckpts | Infra GC with hard quota + retention policy (last 3 / best / per-10k); pre-run free-space check; alert at 80% |
| Long-run interruption (reboot, session loss, power) | goal-mode sessions are not durable | Everything restartable from manifest + last ckpt (M0 acceptance includes resume test); Team-Lead relaunch via startup script; state on disk, never only in agent context |
| Goal-loop tunnel vision | agent "completes" a milestone by weakening criteria | criteria.yaml immutable after milestone start (hash recorded); criteria edits are owner-gated |
| Self-grading collusion | Training agent evaluates itself | Role separation enforced by file permissions: Training cannot write under `eval/`; Eval cannot write under `train/` |
| GPU contention/zombie jobs | crashed run holds VRAM | queue daemon kills CUDA processes not matching the active lock; lock has TTL + heartbeat |
| License contamination of release | NC payloads slip into the public repo | M6 checklist: repo-history scan, manifest cross-check, third-party license table review — owner signs |
